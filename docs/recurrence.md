# Finite recurrence editing

`RecurrenceEditor` stages a `RecurrenceSeries`, previews its finite occurrences and
applies an explicit series or occurrence change. A local preview does not book a
resource or create a calendar backend. The component owns its editing form; place
it outside another native form.

## Dates, zones and termination

Rules are daily or weekly with an interval from 1 to 52. Weekly days use ISO
Monday=1 through Sunday=7. Supply a real civil `startDate`, a wall-clock `HH:mm`
time, an explicit IANA `timeZone` or UTC, elapsed duration and exactly one end:
`count` or inclusive civil `until`. Browser timezone is not inferred.

The Temporal-based engine requires an explicit disambiguation policy. `reject`
refuses repeated or nonexistent wall times; `earlier` or `later` deliberately
chooses the corresponding instant, including shifting a nonexistent local time
around a DST gap. Duration is elapsed minutes, so its local-clock appearance can
cross a DST boundary. The preview displays exact UTC starts/ends and start offsets.

Expansion is bounded to 366 base occurrences and 3,660 scanned days. Skipped base
occurrences still count toward `count`. At most 366 exceptions are supported.
The preview shows at most 24 rows, defaulting to eight, while validating the whole
finite series. This is not arbitrary RRULE support, monthly/yearly recurrence or
an unbounded background scheduler.

## Staging and edit scope

Field changes remain drafts until Apply. Cancel or Escape restores the accepted
snapshot. Invalid fields are linked from the error summary; applying a DST-invalid
rule focuses its policy control. Read-only mode preserves inspection while
preventing changes. Local theme, direction, messages and motion follow UIProvider.

Choose **Entire series** for a complete rule replacement, or **One occurrence**
for an exception keyed by its original civil date. A skip suppresses that base
occurrence. An override supplies explicit whole-minute ISO instants and may name
another resource. Original-date selection includes dates already skipped by an
exception. Existing exceptions must remain valid after a series-rule replacement;
orphaned exceptions are rejected rather than silently deleted.

Changing a touched draft's scope or original date requires applying or cancelling
first. The application must authorise occurrence and whole-series edits separately.
No email, notification or external calendar change is generated by this component.

## Service ownership and uncertain outcomes

`source.save(request, {signal})` receives an immutable request ID, expected revision
and explicit scope. A successful receipt must match that request identity and its
expected complete snapshot. A validation result means the source did not apply
the request. A revision conflict supplies the current authoritative series.

On a thrown error or malformed/mismatched receipt, the outcome remains unknown.
Editing is locked. **Retry same request** resends the identical body and ID; it
does not create a second operation. Optional `source.receipt(requestId, {signal})`
reconciles a durable outcome without resending. A null receipt is not evidence of
failure and keeps the operation uncertain. Do not turn a transport abort into a
claim that the service rolled back.

New supplied revisions or source identities preserve the draft and require
deliberate adoption. Same-source revision conflicts may be reviewed against the
latest snapshot before another Apply. A cross-source draft is not silently rebased.
An old request's receipt cannot replace a newer supplied revision. Optional
`source.load({signal})` supports explicit reload; without it, the supplied snapshot
is used. `onSeriesChange` reports confirmed snapshots to the host.

Without a source, Apply updates a local snapshot and invokes the host callback;
the status explicitly says no service request was sent. The included memory source
is a bounded reference for examples, with in-memory idempotency receipts. A real
service owns authentication, resource permissions, atomic revision checks and
durable request receipts. The host must retain unresolved request identities across
navigation or reload when that is required; component memory is not durable storage.
